# CLI Device Login via Better Auth Device Authorization — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Replace the hand-rolled loopback browser login (`packages/backend/src/routes/cli.ts` + `packages/cli/src/login.rs`) with the Better Auth Device Authorization plugin's first-party flow (RFC 8628): no local HTTP server, no session token in a URL fragment.

**Architecture:** The backend mounts Better Auth's `deviceAuthorization` plugin (already present in better-auth 1.6.25 — verified in node_modules, so NO version bump is needed). It adds a `deviceCode` table plus endpoints `/api/auth/device/code`, `/api/auth/device/token`, `/api/auth/device/approve`, `/api/auth/device/deny`, and a verification page at `/device`. The Rust CLI POSTs `/device/code`, shows the user code, polls `/device/token` until approval, then stores the resulting Better Auth session token (same credential shape as today, so `bearer()` and `packages/cli/src/api.rs` are unchanged).

**Tech Stack:** Bun workspaces; Hono on Cloudflare Workers + D1 + Drizzle; better-auth ^1.6.25 (`deviceAuthorization`, `deviceAuthorizationClient`); Rust CLI (reqwest, tokio).

**Key docs** (live):

- https://better-auth.com/docs/plugins/device-authorization
- Local typings confirm available options: `verificationUri`, `expiresIn`, `interval`, `validateClient`, `onDeviceAuthRequest` (`node_modules/better-auth/dist/plugins/device-authorization/index.d.mts`)
- Schema table `deviceCode`: deviceCode, userCode, userId?, expiresAt, status (pending|approved|denied), lastPolledAt?, pollingInterval?, clientId?, scope? — all ≤191 chars

## Current context / assumptions

- Branch: `feat/cli-browser-login`. Current flow (loopback callback + fragment token) works and is committed; this plan replaces it.
- Backend auth instance is created per-request in `packages/backend/src/lib/auth.ts` (`createAuth(env)`); plugins list already has `bearer()`, `multiSession()`, `openAPI()`.
- Schema barrel: `packages/backend/src/db/schema/index.ts`; migrations generated via `bun run db:generate` in packages/backend (drizzle-kit → `drizzle/*.sql`).
- Router mount point: `app.route("/api/cli", cliLogin)` at `packages/backend/src/index.ts:86`; better-auth handler mounted elsewhere in that file under `/api/auth` (verify exact path when editing).
- CLI login lives in `packages/cli/src/login.rs`; API client attaches `Bearer <session token>` in `packages/cli/src/api.rs`.
- Owner-only access is enforced by OWNER_EMAIL hooks in auth.ts — unchanged.
- Decision made earlier this session: standalone first-party flow now (`/device/token` returns a session token). Upgrading later to oauthProvider 1.7.x device-code grant stays possible because client IDs/scopes shape carries over.
- The plugin needs a user-facing verification page where the signed-in owner types/approves the code. We will serve it from Hono (self-contained HTML like routes/cli.ts today) rather than touching any web frontend.

## Proposed approach

1. Add plugin + `deviceCode` Drizzle table + migration.
2. Build three small backend pages/routes: code-entry page (`GET /device`), approve/deny handling (uses plugin endpoints), success page (polling then completes).
3. Rewrite CLI login: request codes, print/open verification URI (prefer `verification_uri_complete` so the user doesn't type anything when possible), poll with slow-down handling and 5-minute timeout.
4. Delete `routes/cli.ts` and its mount; update tests; keep `--no-open` printing URL+code (SSH-friendly).
5. Optional UX keep-alive: also accept the old loopback flow? No — YAGNI, one path only.

### Task 4: Rewrite CLI login (Rust)

**Files:**

**Step 1: Design the state machine first (TDD):**

```
request_codes(): POST {base}/api/auth/device/code  body: client_id=webmarks-cli&scope=openid profile
  -> { device_code, user_code, verification_uri, verification_uri_complete?, expires_in, interval }
poll(interval): POST {base}/api/auth/device/token
  body: grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=&client_id=
  responses:
   - 200 { access_token (session token), ... }  => done
   - 400 { error: "authorization_pending" }      => sleep interval, retry
   - 400 { error: "slow_down" }                  => interval += 5s, retry
   - 400 { error: "expired_token" | "access_denied" | "invalid_grant" } => bail with message
```

Write a failing unit test over the response→decision mapping using canned JSON bodies.

**Step 2:** Implement with reqwest async client consistent with `api.rs` (reuse its base_url handling and timeout patterns). Print:

```
Open this URL to authorize Webmarks CLI:

  <verification_uri_complete or verification_uri>

Or visit <verification_uri> and enter code: XXXX-XXXX
Waiting for approval… (expires in N minutes)
```

Open browser unless `no_open`. Timeout overall at LOGIN_TIMEOUT (keep 5 min constant). Store token via existing Config mechanism (session_token) — unchanged downstream.

## Risks / tradeoffs / open questions

1. **Session token vs OAuth tokens:** first-party flow returns a long-lived Better Auth session token, same as today. Fine for single-owner app; revisit with @better-auth/oauth-provider 1.7.x when scopes/short-lived tokens matter. Requires better-auth upgrade (^1.7.2 peer) — deliberately out of scope now.
2. **Plugin maturity:** docs mark OIDC provider (deprecated cousin) as non-production; device-authorization looks stable and ships in our pinned version — pin exact behavior by adding a small integration test hitting `/device/code` → approve → `/device/token` using vitest-pool-workers.
3. **Verify api names server-side:** this plan assumes `auth.api.deviceApprove/deviceDeny` names from live docs; confirm exact exports in `node_modules/better-auth/dist/plugins/device-authorization/index.d.mts` during Task 3 before writing code.
4. **Unauthenticated surfaces:** sign-in wrapper page must reuse OWNER_EMAIL guards (it hits /sign-in/email which is already guarded by hook) and respect existing rate limiting rules.
5. **Migration coordination:** remote D1 needs `db:migrate-remote` before deploying the CLI release that drops `/api/cli/login`; sequence releases backend-first.
6. **UX regression:** previously signed-in users got instant auto-redirect; now everyone types/confirms a code. Mitigate with `verification_uri_complete` deep link.
